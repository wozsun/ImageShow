## 结论摘要

5.3.0 将并发配置压缩为少数有明确资源所有者的入口：浏览器上传、Server raw PUT、
Server 图片处理和 Server 最终入库各自只有一个公开限制。Upload / Import 共用的 preparation
准入与 Import 下一批后继都按 Normalize 容量派生；接入任务发现容量由对应资源许可派生，存储清理、
迁移和 Commit 字节预算只保留代码内部的唯一执行边界。

Normalize、Commit 和存储内部边界来自 2C4G 四服务同机隔离测量；Upload 的现行默认值按最终
部署选择调整为浏览器 2、Server raw PUT 5。Normalize 保留为 2，Commit 选择 8 并派生半批候补，存储迁移固定为 5，
存储清理固定为一个活动的 provider 中性批量调用。所有动态数量许可保持 FIFO：提额立即
补位，降额允许已活动工作自然排空，取消、断开和停机均释放等待项与许可。

本版同时完成 S3 / COS 原生多对象删除、同服务端 CopyObject、跨存储恒定内存流式传输、
导入 metadata 来源策略和若干现行默认值调整。数据库 schema 与业务数据结构沿用 v5.2.2 基线；
`config.json` 以现行完整结构完成默认补齐、结构投影、值校验和原子写回。

发布候选同步更新了 `@aws-sdk/client-s3` 3.1121.0、`@tanstack/react-query`
5.102.8、`react-router` 8.3.1、`zod` 4.5.2、`@vitejs/plugin-react` 6.1.1 和
`@types/node` 26.4.0。这些均为现有主版本范围内的直接依赖更新；Node.js 运行时
支持边界继续保持 `>=26.3.0 <27`。

## 最终公开配置职责

### 并发配置

| RuntimeConfig | 默认值 | 合法范围 | 唯一所有者与作用范围 | 普通设置页 |
| --- | ---: | ---: | --- | --- |
| `upload.browser_concurrency` | 2 | 1–8 | 单个活动浏览器页面；共享预览、凭据请求和 raw PUT lane | 可编辑 |
| `upload.raw_concurrency` | 5 | 1–8 | 单个 Server 进程；合计限制全部页面与直接 API 的 raw PUT | 高级配置 |
| `normalize.concurrency` | 2 | 1–8 | 单个 Server 进程；Upload、Import 和维护入口共享图片处理许可 | 可编辑 |
| `ingestion.commit_concurrency` | 8 | 1–16 | 单个 Server 进程；Upload、Import 共享最终入库许可 | 可编辑 |

这些字段均位于各自业务阶段；单机单容器部署下天然覆盖唯一 Server 进程。
`normalize.concurrency=N` 还派生两类来源共用的 prepare / staging publication 准入与 Import 后继窗口，但不改变最终提交并发；
`ingestion.commit_concurrency=N` 只约束正式对象采用、数据库提交、发布与收尾，不改变
下载或转码数量。

### 导入 metadata 策略

- `import.keep_original_link` 是来源白名单，默认值为 `["url", "jsonl", "weibo"]`；环境变量
  `IMPORT_KEEP_ORIGINAL_LINK` 使用严格 JSON 数组 `'["url","jsonl","weibo"]'`，
  允许按 `url`、`jsonl`、`weibo` 组合，也允许显式写 `[]`。
- 只有白名单中的来源把实际下载 URL 写入可公开使用的 `original`。未列出的来源仍正常
  下载、处理和入库，来源页面 `source` 不受该白名单影响。
- `weibo.source_enabled` 默认 `true`，只控制微博导入是否填写帖子页面 `source`；它不改变
  图片下载、`original` 白名单或其他来源。
- Server 在接管和首次 Commit intent 冻结时执行同一权威投影。冻结后的重试复用冻结值，
  正式入库后的管理员人工编辑继续使用普通图片编辑语义。
- `config.json` 按现行完整结构补齐默认值、清理结构外字段并校验当前值后原子写回。

### 配置路径与环境变量

RuntimeConfig 的每个叶路径均通过“`.` 转 `_` 后转大写”得到唯一环境变量名，源码契约逐项核对
默认结构、schema、绑定顺序、`.env.example` 与权威配置表。现行站点路径为
`site.icon` / `SITE_ICON`、`site.gallery.limit` / `SITE_GALLERY_LIMIT` 与
`site.random_method` / `SITE_RANDOM_METHOD`。`m=json` 仍是单次随机图请求参数，不属于
`site.random_method` 的配置值。

`import.keep_original_link`、`weibo.request_delay_seconds` 与 `altcha.counter_range` 的环境值均使用
严格 JSON 数组。来源白名单会规范化去重；两个范围数组都由 schema 固定长度、整数边界与上下界顺序。
配置文件始终投影到上述现行结构，生产值可在升级后按已记录内容写回。

## 代码职责与命名收口

- Ingestion 对外批次顺序统一使用 `batch_position` / `batchPosition`，与 `batch_key` / `batchKey`
  共同表达 Upload、URL、JSONL 和微博的同批稳定顺序；`manifest_line` 只保留 JSONL 清单行号职责。
- Import canonical 的 `import_download`、API 的 `download_url` 与 Web 的 `downloadUrl` 在接入阶段
  携带实际图片下载地址；白名单允许时，同一个值写入 metadata `original` 并成为可公开使用的
  原图链接。metadata `source` 表示来源页面，例如微博帖子页。
- 内部白名单以 `importTypesKeepingOriginalLink` 表示“保留原图链接的导入类型集合”；导入类型、
  接入阶段下载地址与图片来源页面分别使用独立名称。
- Worker 的派生容量统一命名为 pre-commit dispatch slot 与 commit dispatch window；真正协调取消、
  PostgreSQL 不可逆边界和 fencing 的 `IngestionIrreversibleCoordinator` 保留其协调器名称。
- 单图迁移原语位于 `storage/migration/image.ts`，所选图片入口位于
  `images/selected-image-storage-migration.ts`，整后端图片迁移位于
  `storage/migration/backend-images.ts`；对象删除许可位于 `storage/objects/removal-admission.ts`。
- 存储访问对象使用 `StorageAccess`，写入参数使用 `contentType`，迁移与 relocation 的补偿函数以
  enqueue cleanup 明确表示持久清理接管，不把排队清理误写成同步丢弃。
- Web 的 URL 来源解析、任务去重与重试复位分别位于 `import-job-source.ts`、
  `ingestion-job-deduplication.ts` 和 `ingestion-job-retry.ts`；raw XHR 批处理位于
  `raw-upload-batch.ts`。队列写入口使用 `producerApi`，导入来源共用 `addParsedImports`。
- 配置包大小与存储后端数量常量归 `appConfig.configPackage`；Ingestion session 扫描、孤儿清理
  后端硬边界及一次性 raw / staging 清理重试容量都以各自职责命名。

## 内部调度与资源所有者

下列值属于实现策略，不是 RuntimeConfig，也不增加环境变量：

| 内部边界 | 最终值 | 作用 |
| --- | ---: | --- |
| Sharp 每图线程 | 1 | 避免单图编码在 2 核机器上放大线程竞争 |
| Ingestion preparation | `N` | Upload / Import 共用；从等待 Normalize 持有到两个 `_uploads` 对象及 ready canonical 发布 |
| pre-commit dispatch slot | 每来源 `N` | 从 `normalize.concurrency=N` 派生；Import 在 Normalize 准入时交还，Upload prepare 完成时交还 |
| Commit intent worker | 10 | 批量读取事实后建立短、不可变提交意图 |
| Commit prepared 字节预算 | 256 MiB | FIFO 加权许可；超预算的单个合法对象在空闲时独占执行 |
| Commit dispatch window | `N + ceil(N / 2)` | 从 `ingestion.commit_concurrency=N` 派生半批候补 |
| 存储清理活动调用 | 1 | 全进程共享 provider 中性 `removeObjects(1…N)` 准入 |
| 存储对象状态确认 worker | 8 | 单个 `1…N` 调用内部并行 preflight / confirmation，不增加活动清理调用数 |
| local 批量删除 worker | 8 | 单个 local driver 调用内部并行文件删除 |
| 存储迁移活动数 | 5 | 所选图片、整后端和主题重分配共享同一逐图边界 |
| staging 孤儿清理批次 | 100 | 大集合渐进确认和删除，避免一次完整预检 |

### 动态许可器

普通数量许可器和加权许可器都以等待队列为先。只要已经有 waiter，新请求就不能走快路径
越队；RuntimeConfig owner 收到变更后同步 `refresh()`，升额立即按 FIFO 补位，降额则停止发放
新许可并等待活动项排空。等待取消、交接取消、活动取消、任务异常和启动 hook 异常都释放
精确许可；Weighted oversize 只在当前没有其他活动字节时独占运行。

### Upload

浏览器页面使用一个 FIFO owner 串起 `preview → credential → raw`。同一次文件选择完成整段
交接后，下一次选择才可进入，避免大量新预览饿死已经签发且有短 TTL 的 raw 凭据。

Server 在凭据结构和签名通过后、claim 与正文读取前取得唯一 raw 许可。许可覆盖流式 part
写入、大小和尺寸复核、raw 原子发布、存储目标复核、canonical 转换与失败清理；页面数量、
管理员数量和直接 API 都不会建立额外 lane。

### Import 与 Normalize

Import queued 与恢复后的 received 共用跨扫描页 FIFO。下载及已下载但尚未取得 Normalize
许可的项目合计不超过 `normalize.concurrency`；某项真正取得图片处理许可时立即让出后继名额，
下一项才开始下载。因此在生产环境下载快、转码慢的前提下，只保留“处理当前批时下载下一批”。
该窗口直接由 `normalize.concurrency` 派生。Upload prepare 同样按 Normalize 容量持有 pre-commit dispatch slot，slot
保留到本项完成。两种来源另外共用唯一进程级 preparation owner，合计最多 `N` 项从等待 Normalize
推进到 staging 与 ready 发布；尚未取得该许可的 Import 后继只持有磁盘 raw。中央 Normalize 许可是两类来源与维护入口唯一的图片处理准入。两类补位分别使用 frozen-tail
游标，从最早 runnable
位置继续扫描，不因 Commit 前缀、周期 tick 或另一来源占满而改写 FIFO。

Normalize 许可由 Upload、Import、缩略图维修和亮度重算共同使用，覆盖转码、缩略图和亮度识别。
Prepared 存储发布不占用 Normalize CPU 许可，但继续占用两种来源共用的 preparation 许可，直至
两个 `_uploads` 对象及 ready canonical 成功发布；慢存储既不能长期阻塞公共 CPU 处理入口，也
不能让持有 Prepared Buffer 的任务随 Import 队列增长。

### Commit

最终入库数量许可在取得会话锁、存储共享锁和数据库事务连接之前生效，并与 256 MiB prepared
字节许可共同覆盖正式对象复制、PostgreSQL CAS/事务、Redis/缓存发布、staging 清理和结果水合。
等待数量或字节许可的任务仍计入派生候补，不能被重复发现和预取。

Commit Worker 在活动任务降至 `N` 时事件驱动补位，不等待周期 tick；其独立 frozen-tail
游标不会重置接入任务扫描。Normalize 热加载升额同时刷新实际许可、共享 preparation 与 Import / Upload pre-commit
dispatch slot，降额停止新增并让已有 slot 自然排空。Worker stop 会注销监听、清空补位请求并阻止迟到
完成回调继续领取任务。

### 微博请求

访客握手和帖子 metadata 请求由一个进程级 scheduler 串行执行。多个批次每次各执行一项后轮转；
进程只维护一个访客身份和一个创建中的 Promise。明确拒绝身份时不重试当前帖子，下一项才创建
新身份。相邻帖子请求按 `weibo.request_delay_seconds=[2,5]` 均匀随机等待；图片链接解析完即离开微博调度器，后续
下载进入普通 Import 后继窗口。

### Advisory lock、取消和收尾

Advisory lock 的调度信号只负责连接 checkout 与锁获取；锁内回调独立响应父锁或当前连接失效。
调用方取消会移除尚未取得资源许可的工作，已经进入不可逆边界的短操作则完整接收结果，再由
CAS、execution token、单图锁和清理 guard 收敛。Worker 已发出的 lease renewal 即使晚于 handler
结束也必须参与最终 fencing，不能吞掉迟到的租约丢失或续租异常。

## 存储删除与迁移

### Provider 中性 1…N 删除

存储 driver 统一提供 `removeObjects(1…N)`，为每个输入返回 `removed`、`missing`、`failed`
或 `unknown`，并保留原顺序。local 单调用内部使用 8 个 worker；S3 / COS 使用原生
`DeleteObjects`，每请求最多 1,000 个 key，超过时在 driver 内顺序分块。

Quiet/Verbose、部分失败、响应丢失、取消、重复输入、未开始分块和畸形响应都由同一逐项模型
处理。COS 请求在签名前生成 XML 正文的 `Content-MD5`。Commit 成功后的 image/thumbnail
staging 以一次 N=2 调用清理，只将 `failed` / `unknown` 键交给有界重试；没有可信响应时才
保留两键。

S3 self-test 的探针对象可能在调用方取消前已经落地，因此清理使用 driver 自身的独立有界预算，
不复用已经取消的信号。业务清理共享一个活动调用；回收站和持久 cleanup job 继续保持对象结果、
数据库条件删除、单图锁与失败重试语义。显式维护按主要资源将缩略图 repair 交给 Normalize 容量、
孤儿 remove 交给 cleanup 容量；repair 替换未采用缩略图时仍通过共享 cleanup 入口确认删除。两类
同时推进，取消或失败时在独占位置锁内等待已经启动的两个资源池全部收口，正常结果按原候选顺序合并。

### 存储迁移

兼容的 S3 / COS 迁移优先使用条件 `CopyObject`：源对象只流式校验一次，数据库 size/MD5
作为期望值，复制使用该次读取获得的强 ETag 作为 `CopySourceIfMatch`。不兼容的 local/S3
组合通过同一 provider 中性契约进行恒定内存流式传输；local 使用同目录候选与原子发布，S3 PUT
携带明确长度，media 同时携带 `Content-MD5`。

数据库 MD5 不再触发第二次完整摘要读取。已有目标的异常分支仍比较源/目标强摘要以拒绝冲突，
源缺失统一映射为领域内的 missing 结果。目标发布前保留传输校验，单图锁、PostgreSQL CAS、
COMMIT 回包丢失恢复、失败候选清理和源对象延迟删除语义均未改变。

CopyObject 的不确定响应窗口由持久 guard 覆盖实际复制、目标摘要验证和远端结算。Guard handler
取得同一单图锁后按 job id 与 execution token 重读 payload，避免用旧截止时间把迟到发布误判为
终态并遗留对象。

## 隔离测量

### 环境与安全边界

每个有效样本使用独立 Compose project、PostgreSQL、Redis、应用 volume、网络、对象前缀和
父 cgroup。PostgreSQL、Redis、nginx 与生产 ImageShow 镜像共同受 `2 vCPU / 4 GiB RAM /
2 GiB Swap / 4096 PIDs` 约束；测试完成后删除本轮容器、卷、网络、浏览器 profile、父 cgroup
及唯一 COS 前缀。默认 Compose、现有数据库、Redis、`data/` 和长期对象均未参与。

首轮 450 图组合基线全部 ready，p50/p95/p99 为 `5.364 / 8.398 / 13.406 s`，共同内存峰值
约 `973 MiB`，ImageShow CPU 峰值 `194.44%`，Swap、OOM、PostgreSQL waiting 和 Redis
错误回复均为 0。它确认 2 核 CPU 是主要瓶颈，内存仍有足够余量。

### Upload、下载与 Normalize

### Commit 筛选

100 张小图用于完整扫描 `N=1/2/4/8/10/12/16` 与四种候补策略：

| 策略 | 最佳 N / 窗口 | 稳定中位吞吐 | 平均 runnable 页 / Redis 命令 | 许可 p95 空隙 |
| --- | --- | ---: | --- | ---: |

| 一个候补 `N+1` | 16 / 17 | 58.88 img/s | 103.7 / 296.0k | 0 ms |
| 半批候补 `N+ceil(N/2)` | 8 / 12 | 80.96 img/s | 33.7 / 113.1k | 0 ms |
| 完整下一批 `2N` | 12 / 24 | 71.00 img/s | 22.3 / 75.3k | 0 ms |

3600 图长测中，完整下一批 8 的最高稳定中位为 `70.18 img/s`，90% 门槛为
`63.16 img/s`。半批 8 的中位/最差为 `67.72 / 63.26 img/s`，分别达到最高值的
`96.5% / 94.2%`，同时比完整下一批少 4 个 waiter/Promise/AbortController，最大内存峰值
低 25 MiB，因此选择满足吞吐的最小派生窗口。

半批 4 的中位仅 `50.54 img/s`；补测 `N=2 / 2N` 的中位为 `60.78 img/s`，也低于门槛。
默认 8 是已测候选中的最小合格数量。最终精确代码再次完成 3600 图诊断：`69.17 img/s`，
p50/p95/p99 `22.49 / 48.76 / 51.40 s`，窗口/活动/等待为 `12 / 8 / 4`，许可交接空隙 0；
共 1,012 个 runnable 页、6.39M Redis 命令，进程 RSS/父 cgroup 峰值约 `358 / 582 MiB`，
事件循环 p99 `30.15 ms`，Swap、OOM、memory pressure 和主池 waiting 均为 0。完整排空后
Worker Promise、AbortController、数量/字节许可及 3,600 个 guard 全部归零。

10 张 96 MiB 样本得到 `1.83 img/s`，p50/p95/p99 为 `2.77 / 5.44 / 5.44 s`。

200 张 Upload/Import 各半的混合积压为 `52.03 img/s`，p95/p99 `3.63 / 3.80 s`，

许可和 staging 均为 0，停机时替代 Worker 能从 Redis canonical 恢复 24 项并完成。
