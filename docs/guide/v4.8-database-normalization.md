# v4.8 数据库一次性归一化

本页只适用于已经部署 `v4.8.8`、且数据库由旧版持续升级而来的单实例。它指导人工删除
`metadata.extra`、`background_job.result`，并把存储与后台任务类型 CHECK 收窄到当前值。
脚本不修改业务行、图片 / 缩略图对象、词表、管理员、任务 payload 或 Redis；`v4.8.9`
会在生产执行成功并经人工确认后删除脚本与本页。

不要把这个入口接到应用启动、容器 entrypoint、健康检查或定时任务。默认命令和显式
`--check` 都只读；只有 `--apply` 会执行 DDL。以下步骤假定仓库的单个 `compose.yaml` 和
`imageshow`、`postgresql`、`redis` 三个服务，服务名不同时应替换为实际名称。

## 1. 确认版本、停止应用并创建可恢复备份

先确认当前应用镜像确实是 `v4.8.8`，随后只停止 ImageShow；PostgreSQL 与 Redis 保持
运行。停机后不得再启动第二个应用或保留临时管理连接。把最终备份保存在容器和 Compose
volume 之外，保证备份完成后没有遗漏的新写入：

```bash
docker compose exec imageshow node -p "require('./package.json').version"
docker compose stop imageshow
docker compose ps
docker compose exec -T postgresql sh -lc \
  'pg_dump --format=custom --no-owner --no-privileges --username="$POSTGRES_USER" --dbname="$POSTGRES_DB"' \
  > imageshow-before-v4.8-normalization.dump
```

归档包含管理员哈希和存储凭据等敏感数据库内容，应限制文件权限并按生产备份策略加密保存。

至少用 `pg_restore --list` 验证归档可读；正式执行前还应按自己的 PostgreSQL 恢复策略，把
它还原到独立的临时数据库并实际查询。下面的名称只用于恢复演练，不能指向生产库：

```bash
docker compose exec -T postgresql sh -lc \
  'pg_restore --list -' \
  < imageshow-before-v4.8-normalization.dump > imageshow-before-v4.8-normalization.list

docker compose exec -T postgresql sh -lc \
  'createdb --username="$POSTGRES_USER" imageshow_v48_restore_check'
docker compose exec -T postgresql sh -lc \
  'pg_restore --exit-on-error --no-owner --no-privileges --username="$POSTGRES_USER" --dbname=imageshow_v48_restore_check' \
  < imageshow-before-v4.8-normalization.dump
docker compose exec -T postgresql sh -lc \
  'psql --username="$POSTGRES_USER" --dbname=imageshow_v48_restore_check --command="SELECT count(*) AS images FROM metadata"'
```

确认演练库可用后，删除这个精确命名的临时库。不要删除或重建生产数据库：

```bash
docker compose exec -T postgresql sh -lc \
  'dropdb --username="$POSTGRES_USER" imageshow_v48_restore_check'
```

## 2. 只读检查

确认没有第二个应用实例或临时管理连接仍连接目标数据库：

```bash
docker compose run --rm --no-deps imageshow \
  npm run database:normalize:v4.8 -- --check
```

检查 JSON 中以下内容后再继续：

- `target` 是预期数据库、角色和 PostgreSQL 实例；
- `row_counts.webdav` 与 `row_counts.thumb_generate` 均为 `0`；
- 两个遗留列的 `non_null_rows`、`non_default_rows` 已记录；非默认历史值不会阻止已计划的
  删列，但必须能从备份恢复；
- 两个 CHECK 只处于 `legacy` 或 `current` 状态；
- `other_client_connections`、`blockers` 均为空，`ready_to_apply` 为 `true`；
- `pending_ddl` 只包含本页开头列出的两次删列和两个 CHECK 的替换。

脚本发现 WebDAV / `thumb.generate` / 其他未知类型行、自定义列依赖、未知约束形状、权限
不足或其他数据库连接时以非零状态退出。不要删除业务行、手工 `CASCADE`，也不要修改脚本
绕过检查；保留备份和现场，先查明来源。

## 3. 在一个事务中执行并复查

显式 `--apply` 表示操作者已经核对了备份、目标和停机条件。脚本在同一事务中取得三张表的
`ACCESS EXCLUSIVE` 锁，重新检查前置条件，执行无 `CASCADE` 的精确 DDL，再检查最终形状；
任何 DDL 或检查失败都会回滚整个事务。

```bash
docker compose run --rm --no-deps imageshow \
  npm run database:normalize:v4.8 -- --apply
docker compose run --rm --no-deps imageshow \
  npm run database:normalize:v4.8 -- --check
```

成功的 apply 输出 `status: "applied"`；已归一化数据库再次执行时输出
`status: "already_normalized"` 且 `executed_ddl` 为空。最终 check 应满足：遗留列不存在、
两项 CHECK 为 `current`、`pending_ddl` 和 `blockers` 为空。若连接在 COMMIT 回包后中断，
不要猜测结果，重新运行只读 check。

## 4. 启动和验收

```bash
docker compose up -d imageshow
docker compose exec imageshow node packages/server/dist/healthcheck-cli.js
docker compose ps
```

随后核对 `/readyz`、登录、图库、单图 / 批量编辑、删除 / 恢复 / 彻底删除、上传、local
原图与缩略图读取，以及至少一个实际配置的 S3 代表性读写。源码工作区还应执行：

```bash
npm run check
node --env-file-if-exists=.env --test tests/final-baseline.test.ts tests/final-server.test.ts
npm run test:final:web
```

全部通过后保留备份，并明确确认生产归一化完成；在此之前不得开始 `v4.8.9`。

## 失败恢复

apply 在 COMMIT 前失败时会自动回滚，先用 `--check` 证明原形状仍在，再启动原
`v4.8.8` 应用。若已提交后才发现必须恢复，停止应用，不要直接覆盖生产库；先把上述归档
恢复到一个新的精确数据库并完成完整性检查，再按既有 PostgreSQL 切换流程把
`DATABASE_NAME` 指向该恢复库。保留原库和备份，直到恢复后的应用、健康检查及 local / S3
对象读取全部通过。
