# 存储：本地 / S3，多后端并存

后端是「命名实例」而非「类型」——同一类型可注册多个（例如两个不同的 S3 桶）。在后台「设置 → 存储」新建并配置：

- **本地存储**：无需额外配置，图片保存在容器的存储目录。
- **S3 兼容存储**：填写 HTTPS endpoint、region、bucket、access key、secret key、根目录与可选 HTTPS 公开访问域名（public base URL），可点击「设为默认上传位置」。连接超时和流读取空闲超时默认 15 秒，一次 SDK 调用（包含有限重试）的总时限默认 300 秒，三者均可在后端编辑窗口调整；调用方取消会中止当前请求和响应体，超时、非成功响应或解析失败也会释放底层 body。键列举固定请求最多 1000 项的 S3 页面，再以至多 256 项的小批次向上游交付，不在 driver 内累积完整桶列表；分页 token 缺失、重复或成环，连续空截断页、总页数越界，以及返回请求前缀外对象时都明确失败。

本地对象读取与远端 driver 共用上传大小上限和流式缓冲路径，不会用无上限文件读取绕过
`upload.max_file_size_mb`。本地键列举按固定小批次遍历目录并响应取消；S3 则按需获取下一页，
不会为了返回首批结果预取或保存后续页面。不存在的本地目录按空命名空间处理，权限、设备或
其他 I/O 错误则原样上报。管理检查和维护对每个物理后端、每个前缀最多
接纳 10 万个键作为快照，并显式返回列举是否完整：检查可以展示已经确认的问题及“不完整列举”，
但不会从不完整列表推断对象缺失；写维护只在 `media`、`thumbs`、`_uploads` 三个快照全部完整
后才生成修复或删除候选，达到上限或发生 I/O 错误时不把局部结果当成空存储。同一物理
命名空间的多个 slug 合并检查引用，只列举和维护一次，不能因逻辑别名不同而删除仍被引用的对象；
仍有图片引用的每个逻辑 slug 另以其自身 driver 探测可读性，不能由同组可用别名掩盖故障。

检查页的“存储维护”先以只读 `POST /api/admin/check/storage` 展示影响预览；预览不授予写权限，
也不会作为执行依据。超级管理员勾选确认后，唯一写入口
`POST /api/admin/check/storage-maintenance` 取得全局独占位置锁，重新读取 PostgreSQL 与完整
存储快照，再重建原图仍存在的缺失缩略图、更新该次真实修复的 `thumbnail_size`，并清理确认
无引用的 `media`、`thumbs` 和无导入会话所有权的 `_uploads`。活动导入、仍等待导入清理的
会话对象、缺失原图、已消失候选和未完整列举均明确保留或跳过。数据库中
`thumbnail_size=0` 且实体仍在的未收口缩略图会单独列入待重新确认项。预览按物理命名空间去重
受阻项，只把执行端可以再次核对的维修与删除计入可执行数量；仍存在但已非活动状态的导入
会话暂存单独显示为受保护项。响应满足
`requested = repaired + removed + skipped + failed`，并返回每项的后端、前缀、键、动作、结果
及原因；重复执行只处理仍存在的问题。

每个缩略图修复在生成前后都重读当前图片位置，校验原图 MD5，通过当前 local / S3 driver
写入并回读 SHA-256 与大小；写入前先把当前记录的 `thumbnail_size` 条件更新为 `0`，作为
同一字段内的持久重试标记，最终确认后再写入真实大小。数据库未确认最终大小时会尝试删除
本次候选；即使删除也无法确认，下一次维护仍会因该标记重新校验、替换并收口，不会把未知
对象误当作已完成。维修在读取、删除或标记确定缩略图键之前先拒绝仍由 `move.cleanup` 持有的
未完成删除租约，不能与已经发出的远端 DELETE 竞争。检查页维修不调用请求热路径，也不把
缩略图字节写入 `background_job`。独占锁
使上传、分类和迁移不能穿过快照边界；客户端中止只停止尚未开始的项目，已经开始的固定低并发
片会先完成写入验证或安全清理。检查页维修与 `move.cleanup` 完全分责：前者直接重建缩略图，
后者只删除确认未引用的捕获对象，不保存或消费修复字节。

多个后端可同时存在：每张图片记录自己所在的后端（`storage_slug`），读取、缩略图与删除都通过注册表统一解析该图自身的配置和 driver。在**图片编辑窗口**可把单张图迁移到另一后端，在**批量编辑窗口**可批量迁移。迁移目标必须已启用，并且至少让一张所选图片离开当前后端，因此单图编辑不列出图片本身的存储；混合来源批量编辑仍可选择其中一个已启用的来源后端以迁移其余图片。前端只列出可用目标，服务端也在请求入口和逐图执行边界重新校验，直接调用接口不能绕过。数量中性的迁移响应返回 `migrated`、`failed` 及按请求顺序排列的 `results`；每项明确为 `migrated`、`unchanged` 或带安全错误码的 `failed`，已在目标后端的图片不会重复计入迁移数。管理端仅在 `failed=0` 时按完全成功关闭窗口并显示成功提示；请求失败或部分失败会保留迁移窗口并显示逐项原因。分类移动与存储迁移都要求源原图和源缩略图已经存在；缺少缩略图时在复制任何目标对象前返回 `storage_thumbnail_missing`，提示先运行检查页“存储维护”，不会在移动路径隐式生成。

公共与管理 DTO 都只发布一个 `thumb_url`。local 以及无公开 URL 的 S3 由应用读取；配置了
`public_base_url` 的 S3 直接发布最终对象 URL，不先做 HEAD 或应用 302。应用缩略图路由只读
正式 `thumbs` 对象：缺失映射为 404，其他存储错误保持原样，不读取原图、不查 repair receipt，
也不写存储或数据库。浏览器只尝试当前地址一次；加载失败立即显示统一损坏图标，刷新或重新
打开页面才自然重试。回收站对象仍使用鉴权管理路由，不暴露可绕过权限的地址。

异步操作只改变按钮文案、禁用和等待光标，不把所有进行中状态强制提升为主按钮：保存
本身是实心主按钮，保存中继续保持实心蓝色；连接测试、启停和默认后端切换则保留各自
原有的次按钮或状态开关表面。成功与失败结果仍使用对应反馈色。

存储卡片的末端操作由服务端删除策略决定：空闲的自定义后端显示删除并在提交前二次确认；仍有图片时以 storage backend migration 入口替代删除，并与检查页共用同一迁移对话框及 `POST /api/admin/storage/backends/migrate`。这项操作由 storage 域负责，不属于只读检查；卡片入口会锁定当前源后端，源已不存在时禁止提交而不会静默改选其他后端。内置 `local`、默认后端、未清理导入会话或未解决 `move.cleanup` 等情况以原因说明入口替代删除。管理列表以及最终删除冲突响应都返回结构化的 `deletion.action` 与 `deletion.blockers`，前端不再复制一套删除规则。最终删除仍会在独占位置锁内重新读取全部占用，并在数据库计数为空后额外列举 `_uploads`；因此列表加载后新产生的引用、仅存在于存储端的暂存对象或其他竞态仍会被服务端拒绝。删除与整后端迁移在成功、明确失败或响应结果未知后都会刷新权威列表；若删除回执丢失但后端已不存在，确认弹窗随刷新结果收敛关闭。图片、任何尚未清理的导入会话、未解决的 `move.cleanup` 或 `_uploads` 暂存对象均需先移走或清理。

所有会改变图片对象位置的操作共用“全局共享维护锁 + 单图独占锁”。进入锁后重新读取
当前 `storage_slug`、对象键和分类，读取源对象并把原图 / 缩略图复制到目标位置，
再流式回读目标做强摘要校验；media 还必须匹配数据库 MD5。只有全部验证通过才用旧位置
和分类做数据库 CAS，并在同一事务中写入源对象的持久清理凭据。import commit 也取得
同一单图锁，所以并发提交、分类、存储迁移、主题重分配或彻底删除都会串行收敛。候选
补偿和旧对象删除均由持久 `move.cleanup` 任务负责，且只处理本次
调用实际创建或事务明确转交的对象。整后端迁移先 COUNT 并固定本轮最大 UUID：最多
500 张时只读取有限列表，超过边界后按 UUID keyset 每 100 张读取，绝不一次把整个后端
加载进 Node.js。迁移仍逐图复用同一协议，不会持有覆盖整个批次的单一长事务；大批次
只在首尾短暂取得图片缓存写栅栏，期间关闭核心读门，最后按已提交 revision 去重安排一次
后台重建。

单图迁移状态机集中在一个存储领域原语中，管理接口的单图和批量请求只是同一保序列表
编排器中的 1 项或 N 项；整后端分页也逐项调用该原语，不维护第二套 executor、阶段 DTO
或补偿协议。逐项结果明确区分 `migrated`、`unchanged`、图片不存在、源对象缺失和普通失败；
一个成员失败不会回滚已经完成的其他成员。客户端断开会中止当前并发片并等待其对象候选与
持久清理所有权收口，不再启动后续列表成员或读取下一页整后端数据。

迁移用统一的物理命名空间 identity 判断两个 slug 是否指向同一位置：S3 初始 identity
由规范化 endpoint、bucket 和 root path 决定，本地后端由运行时存储目录决定；凭据、
region、path-style、公开 URL 和超时参数
不参与。S3 Endpoint 经服务端证明只是同一命名空间的新访问地址后，注册表会合并
新旧访问 identity 以及所有相交后端的既有集合；之后排队中的 `move.cleanup` 和跨后端
共享判断使用集合包含或交集，不会因连续地址别名变化而失配。
identity 相同时迁移会用目标后端凭据回读并逐字节验证共享对象，再切换数据库归属，
绝不复制或删除对象。identity 不同时，
源原图先与数据库 MD5 核对；目标同名对象已存在时必须逐字节等于源对象，不能只凭
`exists` 跳过。新写入的目标对象也会回读校验，完整性确认后才允许数据库 CAS。

非默认后端可以停用；停用后不再作为新图片或存量图片迁移的写入目标，但已有图片仍可正常读取，也可从该后端迁出到已启用后端。本地存储仅在存在另一个已启用且已设为默认的后端时允许停用，重新启用后才能再次设为默认。

后台存储后端列表按 `type` 返回唯一有效的配置分支：S3 项只含脱敏后的 `s3`，本地项不携带远端配置。每项同时返回删除动作与阻断原因，但不为列表请求远程枚举 `_uploads`。Secret Key 只返回是否已配置的布尔标记，不返回凭据本身。

编辑窗口只提交实际变化的 S3 字段，连接测试也直接使用表单当前值，不会先保存配置；
未重新输入 Secret Key 时，请求省略该字段，服务端通过普通配置 patch 合并沿用数据库中的
当前值，不维护凭据专用兼容分支。测试会写入、读取并在 `finally` 中删除专用探针对象，
再确认对象确实不存在；测试失败不会把尚未确认的字段写入数据库。

S3 的 bucket / root path 是不可在用修改的物理布局
字段。修改时服务端持有全局独占位置锁，并在锁内重新统计该 slug 的全部图片、全部
`import_session`（不按状态或 `expires_at` 排除）、未解决的 `move.cleanup` 和
`_uploads` 对象；每个后端的 `_uploads` 只列举一次并复用同一快照。任一仍存在即返回
409，并在管理响应 / 错误详情中提供
`cleanup_job_count`。清理任务的 `pending`、`running` 和所有 `failed` 均视为未解决；
管理响应另返回失败数与耗尽重试数。存储卡片可把该后端已耗尽的任务重置为
`pending`，清空错误与重试状态后交给 Worker 重新核验；任务对象已被人工清除时，核验
确认不存在即可自然完成。对应超级管理员接口为
`POST /api/admin/storage/backends/:slug/cleanup/retry`，不会提供直接删除或未经确认忽略
任务的入口。页面会在仍有可运行或待重试的清理任务时自动刷新占用计数；若只剩已耗尽
且等待管理员重试的任务则停止轮询，避免空闲页面持续请求。
导入创建、prepared 暂存写入、commit、取消和过期暂存清理都持有同一位置锁的
共享模式，因此不能在检查后又把暂存写到旧位置。锁连接丢失会发送中止信号并等待
回调收口；raw、processed image 与 thumbnail 都使用尝试级唯一键，且 `execution_token`
与 `raw_token` 必须匹配才能发布对应会话状态，因此迟到写入不能覆盖或发布新执行者的
候选。正式候选与旧位置删除由重新取得单图锁、在删除边界重读真值的 `move.cleanup`
执行；未解决任务同时是对应物理对象的删除租约，所有正式写入路径在任务终结前都拒绝
采用相同键，封闭远端删除请求发出后失锁的窗口。显示名、启停、默认项和排序只更新
注册表快照，不取得独占位置锁，也不退役仍可复用的 driver。公开 URL 只参与响应地址投影，
同样不属于 driver 身份；仅修改它只校验 HTTPS 格式并保存，不执行远端存储探针。凭据、
Endpoint、region、bucket、root path、path-style 和请求时限才组成连接签名。注册表发布新的
PostgreSQL 快照时按该签名原子替换映射，同签名继续复用，
失去引用的旧 driver 立即拒绝新操作；已经进入的普通请求会继续到结算，已返回的对象流则持有
引用直到 EOF、取消或错误，最后只关闭底层 client 一次。这里不再维护 graceful / force 两套
关闭状态机或 driver 私有超时；停机先停止 HTTP 接收并等待真实活动引用排空，进程级 45 秒
硬上限统一覆盖 driver、Redis、PostgreSQL 与其余资源收口。

S3 Endpoint 是可验证的访问地址：即使后端仍在使用，编辑窗口也允许修改。保存时服务端
在全局独占位置锁和该后端配置锁内，分别通过旧地址和候选地址各取得一次完整
`_uploads` 快照，要求所有 attempt 级键及其会话映射完全一致；若存在正式图片，还会用
候选地址对一张既有对象执行有界 Range GET。随后旧地址写入、候选地址读取一段随机挑战，
再反向执行一次，并精确清理两个随机探针。全部通过才在同一持锁数据库会话内更新
Endpoint，并把全部相交后端的 identity 合并为同一连通分量；候选不可访问、快照不同、
双向挑战不同或探针清理失败都会保留原配置。事务 COMMIT 回包丢失时会按 xid8 查询
最终提交状态；结果仍未知时返回明确的刷新提示，不会误称旧配置必然保留。完全
没有图片、导入会话、清理任务、暂存对象、历史 identity 或同命名空间注册项的独立空
后端仍可把 Endpoint 改到新位置，此时会建立新 identity；已知共享关系即使该 slug 自身
为空也必须继续完成同命名空间证明。

对象位置切换后的延迟 `move.cleanup` 会把入队时的物理命名空间 identity 连同后端、
前缀和对象键一起持久化。执行时取得同一单图锁，先确认 slug 仍指向原 identity，再按
当前位置重读 PostgreSQL 引用；正式对象写入还会检查未解决任务的删除租约，因此不可取消的迟到
DELETE 与后继采用不会并发。租约既检查目标直接包含的历史 identity，也会沿清理后端
当前仍成立的共享命名空间关系传播，因此重绑后新建的同 Endpoint slug 同样不能绕过
旧地址留下的删除租约。对象若已成为当前位置则保留，避免旧补偿任务删除当前图片；任务不读取
或写入 `thumbnail_size`，也不生成、校验或采用缩略图。
运行中的确定性任务若再次收到同一清理请求，会持久记录 rerun 请求，并在当前处理成功
落库时重新变为 `pending`，不会丢失 handler 完成与状态更新之间的窄窗口唤醒。每次
driver DELETE 返回后还会重新确认对象不存在；对象仍存在或确认失败时任务继续持久重试，
并写入包含图片、后端、命名空间、前缀、对象键和原因的结构化错误日志，不回滚已经成功
的数据库位置切换。耗尽任务仍保留删除租约与后端占用关系，等待管理员重新排队。

prepare 会保存 processed image 与缩略图的 SHA-256（图片同时保存 MD5）。import commit
流式校验 `_uploads` 源对象，并优先通过 S3 / 本地驱动的后端内复制生成正式
对象，随后流式回读目标校验；不再为了校验把源和目标同时读成完整 Buffer。正式同名
对象已存在但内容不同返回 `storage_object_conflict`；本次复制成功后回读不一致返回
`storage_transfer_integrity_failed`，便于区分存量冲突与存储端完整性故障。异常补偿只
追踪本次实际创建的候选；数据库位置 CAS 与源对象清理凭据在同一事务提交。若 PostgreSQL
操作或 COMMIT 回包不确定，迁移会在仍持有单图锁时重读真值：已指向目标就采用目标并
确保源清理任务存在，仍指向源就只追踪目标候选，位置未知则保留两端并记录结构化运维
错误。所有 media / thumbs 删除失败都进入统一清理追踪，driver 报告成功也必须重新确认
对象不存在。位置 CAS 与 `ready_image_revision` 在同一事务提交；提交后仍在图片缓存

本地上传与链接下载的原始字节统一先进入服务端 `data/tmp`。服务端在本地完成校验、标准化、缩略图与最终 MD5 后，才把 processed image 和 prepared thumbnail 写入目标后端 `_uploads`。因此无需为存储桶配置浏览器 CORS，远端后端也不会发生“上传 raw 后再下载回来处理”的重复传输。详见[功能与流程](./flows.md#图片导入)。
