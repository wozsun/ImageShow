# ImageShow 提交、推送与发布流程

> 授权见 [AGENTS.md](../../AGENTS.md)，版本、候选定义与提交前要求见 [交付规范](../spec/delivery.md)，候选准备见 [测试与验证](validation.md#编写运行与候选准备)，文案格式见 [提交信息规范](../spec/commit-message.md)。

## 提交与推送

1. 确认当前分支、提交基点和工作树正是已获授权且通过 [审查流程](review.md)的候选，并按交付规范核对目标分支与提交类别。候选有变化时返回审查流程处理。
2. 只暂存候选范围内的确切路径；受忽略的测试凭据、本地记录（报告、证据与留存文件）、`TODO.md`、`.agents/plan/`、`data/` 与 `.env` 不得进入暂存区。分别检查 `git status`、`git diff --cached` 和 `git diff --cached --check`。
3. 提交前按提交信息规范逐项核对拟用消息：基线明确、条目有据（每个 `fix` 对应基线版本中已有的缺陷）、归类准确、描述最终结果，标题与分组结构符合对应类别的格式；发布提交还须核对版本与候选一致。创建提交后，通过 `git show -s --format=%B HEAD` 复核 Git 实际保存的原始正文，再核对提交 SHA、提交树和工作树状态；发现差异时在推送前修正并重新复核。提交后的树必须与获准候选树一致；只授权提交时到此停止。
4. 按授权推送。`dev` 发布提交之后的 main 同步、标签和 GitHub Release 按下文正式发布的顺序执行。

## 正式发布

1. 按上述流程在 `dev` 创建并推送唯一发布提交；已有对应且已验证的发布提交时，核对并复用，完成尚未执行的推送。
2. 等待该提交的 Dev Action 成功：它只发布 `dev` 当前头提交到 Docker Hub、腾讯云 TCR 与阿里云 ACR，并回读三仓 `:dev` 的摘要与 revision；旧任务重跑会在构建前失败，属预期行为。校验规则以 `.github/workflows/publish-dev-image.yml` 为准。
3. 将本地 `main` 纯快进到同一提交并推送，使 `main` 与 `dev` 指向同一个发布提交。
4. 确认发布提交已经进入本地与远端 `main`，再用当前配置密钥创建同名带注释签名标签：`git tag -s`。
5. 执行 `git tag -v`；签名或验证失败立即停止，不退回无签名标签。
6. 推送已验证标签。Release Action 只接受指向 `main` 当前头的标签，只复用三仓中已校验且摘要一致的同提交 `:dev` 镜像添加标签，不重新构建，任一仓库失败即退出；Docker Hub 得到版本与 `latest` 标签，TCR 与 ACR 只移动 `latest`。标签分配与校验规则以 `.github/workflows/publish-release.yml` 为准。
7. 等待 Release Action 成功并确认 GitHub Release 与镜像发布结果。
8. 发布成功后，在 Release 或本地验收记录中核对发布提交、签名标签、Action、镜像摘要和正文，并按 [AGENTS.md 文档规则](../../AGENTS.md#文档规则)整理本版留存文件。

正式发布失败或等待外部结果时，在本地验收记录中保留候选 SHA、当前步骤和恢复条件，如实记为未完成。单纯的远端发布失败时，已完成的开发条目保持完成状态；若暴露了尚未完成的实现或验收工作，则恢复对应 TODO，并返回审查流程按其回退表处理。

任一步真实失败即停止；三仓发布核验全部成功才算发布通过，它不替代也不等于本地完整门禁。远端 `main` 先于远端标签更新；已经推送的版本标签不得移动或改写。

## 云仓推送长时间等待

仅当 Dev Action 已明确完成 Docker Hub 推送、只剩腾讯云 TCR 或阿里云 ACR 仍在运行，且该阶段持续超过 30 分钟时，记录候选 SHA、Action URL、已完成仓库和恢复条件，停止轮询，交由用户人工等待；其间不取消、重跑、手工复制或补推，main 快进与签名标签留到三仓成功之后。

用户确认 Dev Action 三仓成功并明确要求继续后，核对目标 SHA、既有验收和 main 可纯快进，从正式发布第 3 步恢复。失败、取消、Docker Hub 状态不明或有其他未完成步骤时，按失败记录处理。
