# ImageShow 开发流程

> 通用实现与测试原则见 [AGENTS.md](../../AGENTS.md)。本流程默认止于等待用户核查。

开发 → 更新容器 → 等待用户核查 → 按 [交付规范](../spec/delivery.md#审查与提交前要求)完成所需测试与审查 → 按授权发布。测试或复审修复满足 [重新核查条件](../../AGENTS.md#核查与验证边界)时，回到本流程第 5 步，重新核查通过后再继续。

1. 明确用户目标和已授权范围，查看当前分支及工作区改动；涉及版本或结构时按主文件导航读取对应规范。
2. 先读当前实现与调用关系，再按 [实现原则](../../AGENTS.md#实现原则)实施，同步处理本次改动影响的调用方、依赖和文档。
3. 阅读差异并做静态自查：职责、类型使用、调用关系、错误处理、权限、缓存失效、资源释放及无用代码。自查以阅读与判断完成，不运行测试与自动检查命令。
4. 按 [测试准入](../spec/test-admission.md) 判断测试影响，只记录因行为变化失效的现有断言和满足准入条件的缺口；测试代码和夹具留到测试阶段处理。
5. 更新用户用于核查的本地容器，使用资源前完整读取本地测试资源 `tests/local-resources.md`。前后端代码变化执行 `docker compose up -d --build`；仅 Compose / 环境变量变化执行 `docker compose up -d`。README、`docs/` 或本地规则变更沿用运行中的容器。更新容器所需的构建属于开发交付，范围止于构建与启动。
6. 交付访问入口、改动范围、自查结果和待核查事项，然后等待用户。容器启动不代表用户核查或测试通过。用户指出问题时修复并再次更新容器；明确确认核查通过后，按交付规范进入所需的 [测试与验证](validation.md)或 [审查流程](review.md)。

若当前目标依赖尚未授权的测试或测量才能合理决策，先说明待验证问题，取得结果后再继续优化。
