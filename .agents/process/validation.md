# ImageShow 测试与验证

> 用户明确确认容器效果核查通过，或另行明确授权测试工作后进入本流程。测试准入和去留原则见 [测试准入](../spec/test-admission.md)。

## 进入前核对

明确当前候选、允许修改的测试和执行范围；定向测试只覆盖授权范围，版本整理、完整门禁及复审按任务和 [交付规范](../spec/delivery.md#审查与提交前要求)选择适用步骤。阅读现有用例和对应实现；需要真实资源时先读取本地测试资源 `tests/local-resources.md`。按 [公开测试说明](../../scripts/tests/README.md)区分可移植契约测试和本地真实资源验收。改动受跟踪测试的依赖、夹具或临时输出路径时，在只含受跟踪文件的干净检出中验证公开命令。

## 编写、运行与候选准备

1. 按测试准入调整测试；页面样式与交互沿用已核查的结果。
2. 先运行相关测试并修复问题。若修复满足 [重新核查条件](../../AGENTS.md#核查与验证边界)，暂停后续测试，按 [开发流程](development.md)更新容器并等待用户重新核查；确认通过后再继续。
3. 准备版本提交或发布候选时，在此固定候选树、版本、文档和 TODO：
   - 将获准使用的本地额外开发分支以目标 `dev` 为基点整合为最终净改动并处理冲突，整合方式遵守 [交付规范](../spec/delivery.md#版本)的分支历史规则。
   - 按交付规范核对用户确认的版本与范围；需要调整版本时在此锁步更新，并同步写死版本号的本地脚本，后续门禁、复审、提交与发布沿用已锁定的版本。
   - 记录已完成范围及实际验收证据，清理 TODO 已完成项和空标题，保留未完成规格及待验收项，后续依赖改为明确能力或版本。
   - 明确文案基线（过程提交的父提交，或发布提交的上一正式版本），按 [提交信息规范](../spec/commit-message.md)起草最终净变化说明。
4. 按交付规范判断是否需要运行或重跑完整门禁；需要时在授权范围内运行 `npm run verify:release`，记录真实结果、失败原因和未覆盖项。启动前先记录候选指纹，门禁输出与指纹写入 `tests/log/<版本>/`，结束后复核指纹未变。满足所需验证条件后，把当前候选及自查、测试结果交给 [审查流程](review.md)。

## 命令选择

完整门禁的通过结论只来自 `npm run verify:release`；下表命令只用于定位和修复问题。日常开发中的容器更新由 development.md 单独规定。

| 场景 | 命令 / 要求 |
| --- | --- |
| 定位问题 | `npm run check`、`npm run build`、`npm run knip`，或 `verify:source` / `verify:build` / `verify:runtime` 单层 |
| 重跑失败用例 | `scripts/tests/README.md` 中的统一入口、名称筛选和场景选择器 |

- 各层内容以 `package.json` 与 `scripts/tests/` 为准。副作用：`verify:source` 只读源码；`verify:build` 只重建三个 workspace 的 `dist`；`verify:runtime` 创建随机命名的 tmpfs PostgreSQL、Redis、应用容器、网络和临时镜像，只使用这些一次性资源，清理等待相关操作结束，只删除本次创建的对象；总入口按 source → build → runtime 失败即停；各层可分别执行，`verify:runtime` 需先完成项目构建。
- 按交付规范仍有效的完整门禁结果覆盖其各单项命令；变化后的处理见 [审查流程](review.md)，GitHub Actions 成功不替代本地验收。
