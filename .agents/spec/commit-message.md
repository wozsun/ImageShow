# ImageShow 提交信息规范

> 本文件只定义提交与 Release 文案的格式及归类；起草时机见 [测试与验证](../process/validation.md#编写运行与候选准备)，提交与发布顺序见 [提交与发布流程](../process/release.md)。

## 发布提交格式

进入 `dev` 或 `main` 的发布提交采用本节格式，正文汇总该版本的开发、修复、文档、测试和构建等改动。提交信息的摘要与正文使用中文，作者归属由 Git 提交身份记录；首行统一使用发布标题，正文按改动类型使用小写英文分组：

```text
release: vX.Y.Z: <祈使句摘要，最多 50 字，末尾省略句号>

<动机或背景，整段写成一行>

<英文类型>:
- <改动及原因，每项写成一行>
```

`vX.Y.Z` 填入按 [版本规则](delivery.md#版本)确认的候选版本。所有 `dev` 更新与正式发布的标题均使用 `release:`；`feat`、`fix`、`perf`、`refactor`、`style`、`docs`、`test`、`build`、`chore` 用于正文分组，按实际改动选择。配置、部署、文档、界面和其他子系统名称写入对应列表项。正文至少包含一个分组；每个分组以独占一行的 `<英文类型>:` 为标题，下一行起使用 `- ` 列出改动及原因。每种类型集中为一个分组，不同分组之间保留一个空行，即使只有一项也保持同一结构。正文每个段落和每个列表项各占一行，由查看工具自动折行。

## 本地额外开发分支的过程提交

分支使用条件与提交授权见 [AGENTS.md](../../AGENTS.md#任务与权限)。首行可使用 `<英文类型>: <祈使句摘要>`，按本次改动选择 `feat`、`fix`、`test` 等类型；摘要长度、语言及正文分组沿用上述要求。整合为发布提交时，重新按发布范围起草标题与正文。

## 文案基线与归类

- 本地额外开发分支的过程提交以本次提交相对父提交的最终净变化为范围；`dev` 发布提交、Release 说明与版本变更文档，统一以上一个已正式发布版本到发布候选最终树的净变化为范围。起草前明确基线标签和候选提交或工作树，并核对两端差异；父提交恰为上一正式版本时，两种比较范围一致。
- 每条文案都从基线版本使用者或维护者的角度说明最终变化、原因与影响。同一能力的多轮实现和修补合并为一个最终结果，完整撤回或恢复基线原状的改动保留为开发过程信息。
- `fix` 用于修复基线版本中已存在的缺陷。每项修复应能说明基线中的触发条件、错误行为与本次修正结果，并由基线代码、复现结果或已有问题记录核验；分组依据是相对基线的效果。
- 本次新增能力在开发期间完成的修补、交互打磨与资源清理，按最终能力归入对应的 `feat`、`refactor` 等条目；正文选择能帮助使用者或维护者理解结果的细节。同一发布内新引入又修好的问题作为实现过程处理，恢复基线原有正确行为的修补以最终净变化判断是否形成文案条目。
- `perf` 描述最终实现相对同一基线的可验证收益；`refactor` 描述最终保留的职责或结构变化。分组随实际净变化建立，只保留有符合归类依据条目的分组。
- `test` 用于本次提交中实际包含的测试资产变化。本地非 Git 跟踪测试的修改、测试执行结果、子代理审查与门禁完成情况写入交付报告或验收记录，作为发布验证依据。发布提交正文会被 Release Action 直接用作 GitHub Release 说明，起草时按正式版本变更说明逐项核对。
- TODO 只保留未完成项；正式发布说明依据基线差异及清理前保留的完成范围起草：已移除的 TODO 条目按完成范围计入本版变更，未来候选、审查过程和仅存在于本地的测试留在 TODO 或报告中。
