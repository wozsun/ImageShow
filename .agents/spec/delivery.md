# ImageShow 版本、TODO 与交付规范

> 操作顺序见 [版本规划](../process/planning.md)、[测试与验证](../process/validation.md)、[审查流程](../process/review.md)、[提交与发布](../process/release.md)；提交文案格式见 [提交信息规范](commit-message.md)。

## 版本

- 版本号和范围最终以用户确认结果为准。必要时按影响给出 X（产品、体验或架构换代）、Y（大型功能或跨主要模块重整）、Z（现有架构内迭代）的建议；分级只看影响，文件数、问题数量和时长仅作参考，每个版本都有实际内容。候选排列和预排版本不构成实施授权。
- `dev` 只接收发布提交，每个版本以用户确认的完整范围形成一个发布提交；开发、修复、文档、测试和构建等改动统一归入对应发布候选。获准使用的本地额外开发分支可保存过程提交，进入 `dev` 前须整合为发布提交。
- 提交信息中的版本号须与候选根包、三个 workspace 及 lockfile 一致。版本尚未确认时保留工作区改动。

## TODO 与方案

- TODO 只保存未完成工作，顶级分组为“已编排、错误修复、功能开发、性能优化”；后两组可分“长期候选、条件触发”。已编排内容只出现在“已编排”一组；条目保留依赖、触发条件和验收边界。`【可独立】` 表示无未完成技术前置，`【依赖：…】` 只表达技术依赖，`【条件触发】` 按列明条件评估。
- 用户要求给出详细方案时，结合篇幅和信息密度，考虑将方案独立写入 `.agents/plan/` 下按主题命名的 Markdown 文件。采用独立方案时，`TODO.md` 保留简明目标、范围、依赖、触发条件和验收边界，并链接方案文件；详细内容只在方案文件中维护。
- TODO 纳入 Git 须有对应授权，公开内容清理敏感信息及本地证据依赖；必要验收未完成时仍是待办。完成范围与实际证据记入候选说明，发布 SHA、签名标签、Action 和摘要记入 Release 或验收记录。

## 审查与提交前要求

- 主进程负责实现、修复、自查和终审；需要独立复审时，由全新子代理只读覆盖完整候选及其上下文。子代理只在用户明确授权时修改文件或运行测试。
- 候选包括拟提交的受跟踪文件及新文件，含 `AGENTS.md`、`CLAUDE.md` 与 `.agents/` 中的规范、流程与参考。TODO 受跟踪或获准纳入提交时同样属于候选，提交须包含其经审查的清理结果；仍被忽略时保持忽略。提交与发布的实际内容必须与主进程终审确认的候选一致，并满足下表的审查与验证要求。
- 非功能性改动由主进程按实际影响判断，包括不改变功能、可观察行为和运行方式的文档措辞、文档排版与链接整理、普通注释，以及 `AGENTS.md`、`CLAUDE.md` 与 `.agents/` 的改动。可执行逻辑、数据、接口契约、运行配置、依赖、版本号、构建部署方式、部署命令与配置示例或 `scripts/tests/` 中受跟踪的测试与门禁发生变化时，按其他改动处理，不按文件扩展名豁免。

| 候选或后续变化 | 审查与验证要求 |
| --- | --- |
| 整份候选仅含非功能性改动（只适用于本地额外开发分支的过程提交；`dev` 发布提交含版本号更新，按下一行处理） | 主进程核对内容、链接和差异并终审，无需独立复审或完整门禁 |
| 候选包含其他改动 | 全新完整复审、主进程终审及 `npm run verify:release` 通过 |
| 已有审查或验证通过结论，后续仅增加非功能性改动 | 主进程自查新增差异并终审，不重新触发独立复审或完整门禁 |

已有结论只沿用未受影响的部分，新增非功能性改动由主进程自查覆盖；候选原有的未完成审查与验证仍须完成。
